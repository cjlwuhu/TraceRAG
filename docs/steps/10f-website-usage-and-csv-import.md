日期：2026-10-06（Asia/Shanghai）。本记录结合 `docs/steps` 与当前前后端实现回答页面操作问题，并继续修复 10e 已定位但仍需手工副本绕过的 CSV 故障。修改位于 `D:/Project/EasyRAG` 和独立 `D:/Project/RCA`，没有发布代码或登记新的正式案例。

## 1. 页面对象与文件的对应关系

| 对象 | 内容 | 如何取得或使用 |
|---|---|---|
| 原始时序 CSV | `time` 与 CPU、内存、延迟等指标采样 | 工作台“上传 CSV”，交给独立 RCA 工程 |
| `signal-bundle.json` | 检测结果、分析窗口、RCA 候选、指标摘要、配置与指纹 | RCA 信号入口导出；工作台“导入信号包”接受此文件 |
| 运维事件 | 转换后的 `IncidentDocument` 与事件专属指标摘要 | CSV 成功处理或信号包导入后进入下拉框 |
| 观测证据 JSON | 同事件的日志、调用链、拓扑、图像图注及原始资产 | “知识与案例”左侧导入；需要单独准备 |
| 检索证据包 | 本次查询最终选中的证据、排名、来源和参数 | 每次检索产生，随运行与工单独立保存 |
| 工单草稿/人工修订 | 根据证据形成的陈述与建议、逐条人工支持判断 | 草稿生成后进入“工单与复核” |
| 正式历史案例 | 人工确认的症状、根因、实际动作、结果及依据 | 故障调查/处置后由审核者另行填写并发布 |

事件不是原 CSV，也不等同于完整信号包。导入 ID 为 `import-…`，领域事件 ID 为 `inc-…`。相同信号包重复导入可产生多个导入记录。检测/RCA/摘要是不同阶段：关闭 RCA 时仍可生成包含异常与指标的事件；无报警或观测窗口不足时不产生可用于 RAG 的完整事件。

## 2. 工作台如何提问

选择事件后，浏览器提交问题、事件 ID、知识来源和实验配置。服务根据 ID 读取已经保存的事件，不重新上传原 CSV、不重新计算 RCA。默认查询可利用 RCA 候选扩展关键词；这个行为由“RCA 候选扩展查询”控制。

例：“当前异常有哪些候选原因？请指出每个候选的依据、仍缺哪些验证，以及处置前提。”

无事件时选择“运维文档问答（无事件）”和系统范围，提交问题与配置，只检索该范围手册。没有当前事件指标、日志或 RCA 候选，也不使用历史案例。例：“checkoutservice 延迟升高时通常检查哪些指标？”

启用云生成后，模型接收问题、结构化事件信息、可选 RCA 候选和最终证据正文；不会因为选择事件而把原 CSV 或整个知识库发送给生成模型。

## 3. 当前知识库与导入时快照

“当前知识库 + 本事件观测”使用当前 `knowledge/active.json` 指向的手册/案例版本，并加入当前事件的指标及后来附加的观测。查询提交时冻结独立快照，因此排队过程中发布新版本不会改变这次查询。

“导入时快照（复现实验）”固定使用事件首次导入时保存的 `corpus/manifest.jsonl`。之后新增的手册、案例和观测附件不进入该模式。

例：昨天以 V1 导入事件，今天发布 V2 并上传日志。当前模式使用 V2 与本事件指标/新日志；导入时快照使用 V1 与当时的指标。

两种模式均受系统、事件与时间门禁约束。当前事件自己的历史案例不会被检索回该事件；晚于事件发生时间审核的案例也会排除。现在审核的 2023 年基准案例不能反过来成为 2023 年事件实验的“既有知识”。保存案例的用途是未来符合这些规则的新事件类比。

## 4. 工单与人工复核

输入框编辑的是生成草稿中的单条摘要、候选解释、验证步骤或处置建议，不是修改原始检索材料。界面保留引用、风险、处置前提等结构；编辑正文会把该条支持判断重置为“不确定”。

支持判断针对“陈述是否被引用证据支持”，不是根因概率，也不是检索材料是否相关：

- 不确定：尚未核验，或依据不足以作判断。
- 证据支持：引用能支撑本条表述。
- 证据不支持：引用不蕴含该结论，或结论超过证据范围。

例如，指标摘要能支持“观测窗口内延迟均值升高”；仅凭这个摘要不能支持“数据库连接池不足已经确定为根因”。引用能定位、字面文字正确，不等于结论正确。

保存人工修订会新增 `outputs/console/reviews/gen-…/rev-…/review.json` 与 Markdown，记录修订正文、逐条标注、审核人、意见和父版本/来源哈希。可以下载、继续修订、追溯，也可用于人工支持率评估。原工单不会被覆盖。

含“不确定/不支持”时只能标为“仍需修订”；全部支持才可标为“已复核草稿”。保存后依然是根因未确认、动作未执行、未提升为案例。人工修订和正式历史案例是两个独立步骤。

## 5. 观测证据 JSON 到底是哪份文件

这是结构化附件包，不是 `signal-bundle.json`、原 CSV 或任意原始日志。顶层必须为：

```json
{
  "documents": ["KnowledgeDocument 对象，实际应是对象而非此示意字符串"],
  "assets": [{"sha256": "原始资产字节的 SHA256", "base64": "原始资产字节的 Base64"}]
}
```

`documents` 支持 `log/trace/topology/image`，每个对象有正文、来源、原始引用及 metadata 中的系统、源事件、观测时间窗口、资产 SHA256、派生方式。资产已在本机登记时 `assets` 可以为空。后台核对事件、时间范围、证据截止时间及资产哈希。

现有 `src/prepare_multisource_demo.py` 从已准备的 RE2 parquet 提取日志频次、trace 耗时、服务拓扑和指标图图注，写 `manifest.jsonl` 后直接附加；`src/attach_event_evidence.py` 也直接接受清单和资产。当前这些脚本没有导出供网页按钮直接上传的包装 JSON，不能随便从 RCA 输出目录挑一个 JSON 当附件包。

若已经准备好符合契约的 manifest 和原始资产，可从项目根目录使用：

```powershell
& 'D:/miniconda/envs/fastapi_env/python.exe' src/attach_event_evidence.py `
  --event-id 'import-这里换为实际导入ID' `
  --manifest '这里换为观测manifest.jsonl' `
  --asset '这里换为清单引用的原始资产文件'
```

或者按上述契约把清单对象与 Base64 资产封装为单个 JSON，再上传。网页限制 8 MB，大资产走现有本地入口。RE1 的这个 CSV 本身不能产生它没有包含的业务日志或调用链。

## 6. 正式历史案例保存什么

由真实调查/处置人员或审核者填写：标题、症状、确认根因、实际动作、实际结果、核验依据、审核人，并确认人工核验。页面自动关联选择的事件、系统和当前审核时间。

保存时留下原提交 `knowledge/case_reviews/review-…/submission.json`，转换成案例知识文档，并发布“原长期库 + 新案例”的新版本。

当前网页不会自动把问题、RCA 候选、检索排名/分数、证据包、prompt 或原工单复制进案例；网页提交的 `rca_candidates` 是空数组。原 RCA 结果仍在事件内，检索与草稿另存在 `outputs/operations/` 和 `outputs/work_orders/gen-…/`，后者含 `evidence-pack.json`、`work-order.json` 等文件。

想让案例能追溯本次检索，应在核验依据中明确写入事件、工单/证据包 ID 与外部处置记录号。当前依据是人工填写的字符串，系统没有自动验证其指向的证据存在，也没有外部身份认证。保存和勾选只是记录人工声明，不能替代事实调查。

计划 9c 的案例数量为当时状态。本机目前版本记录已有 2 条自报案例，但输入看起来是测试占位，不能据此认定已经收集到真实确认事故。

## 7. 用用户 CSV 串起一次操作

本次实际导入 `RCA/data/RE1/RE1-OB/adservice_cpu/1/data.csv` 后，检测首告警来自 `recommendationservice_cpu`，BARO 第一候选为 `main_mem`，并非根据目录名强制输出 adservice。这些是算法输出，不是确认根因。

1. 上传该原始 CSV，保留检测、BARO、摘要默认开关，点击“处理并导入”。事件及 10 条指标摘要保存后可在下拉框选择。
2. 选择“当前知识库 + 本事件观测”，问“main_mem 候选有哪些依据？是否足以确定原因？还应验证哪些指标？”运行检索与工单。
3. 打开复核。若草稿写“main_mem 已确定为根因”，改为“BARO 将 main_mem 列为候选，尚待验证”，并核对引用是否确实能支持修订表述。
4. 只有取得同事件真实日志/trace 等额外观测，才准备附件包并上传；下一次选择当前模式重新查询会使用新观测。
5. 若之后实际调查与处置完成，另填正式案例。下面仅为假设填写示例，不能当作该 RE1 文件已经证实的真实事故：

| 字段 | 假设的已核验填写内容 |
|---|---|
| 标题 | adservice CPU 资源争用导致请求延迟 |
| 症状 | adservice CPU 持续升高，请求延迟和节流计数同期升高 |
| 确认根因 | 现场进程/资源核查证实压力进程消耗 CPU 配额，造成服务节流 |
| 实际动作 | 停止已确认的压力进程，持续观察 CPU、节流计数和延迟 |
| 实际结果 | 上述指标恢复基线，观察期内未复发 |
| 核验依据 | 实际监控记录号、日志行号、处置工单号，以及本次 gen/pack/事件 ID |

案例保存的是人工确认的事实及依据；本次检索证据包仍是单独文件。这个 RE1 数据集没有随 CSV 给出真实处置与恢复工单，不能只凭路径名和生成草稿填“已核验”。

## 8. 云端重排

新控制台有实际重排器：DashScope `gte-rerank-v2`。流程是先召回/融合候选，再把问题与候选正文交给服务评分重排，最后按证据条数和字符预算打包。默认重排 20 个候选，最终证据上限为 6。BM25 也可以单独搭配云重排，不必开启 Dense。

重排解决的是证据相关性排序，不能补回没有召回的资料，不能确认故障根因，也不负责生成工单正文。

“云端”是当前选型：新控制台接的是远程 API。旧 EasyRAG Pipeline 留有本地 CrossEncoder/BGE 重排实现，但未接入此控制台，当前所配本地模型目录也不存在；不能称为现成可用的本地模式。小型本地重排器并非原理上不可运行。

使用时需保存有效 Qwen 凭据、开启设置中的 Cloud 总开关，再在实验配置启用云端重排。Cloud 开启不会自动启用重排。鉴权/额度/网络错误会明确失败，不会静默切回离线。查询和候选正文会提交给外部重排服务。保存的凭据状态不等于已测试有效，本轮未调用云接口。
